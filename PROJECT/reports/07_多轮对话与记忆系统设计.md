# 多轮工具规划与记忆系统：工程设计与自然短会话评测

> 本文从多轮记忆设计的视频材料出发，并按本项目“只输出有序工具 ID、不生成对话回复”的边界实现与验证。评测使用开发/测试各计划 1,000 段的自然短会话、十二个递进候选和一次性独立测试；所有结果均可追溯到机器可读产物。

## 1. 视频讲了什么

视频讨论的问题是：模型上下文窗口固定为 8K Token 时，怎样支撑 100 轮对话，并在第 80 轮仍找回第 3 轮确认过的信息。核心观点不是把全部历史塞进 Prompt，也不是直接换更大上下文模型，而是把上下文窗口当作有限预算，由一个调度层按需装入不同类型的记忆。

| 时间 | 核心内容 |
|---|---|
| 00:00–00:56 | 提出 100 轮对话与 8K 窗口冲突；只截断旧消息会丢失早期结论，只把历史存入向量库又没有解决窗口内如何分配的问题。 |
| 00:56–01:52 | 解释为什么小窗口更考验工程能力：上下文会直接影响推理成本、显存占用和延迟。 |
| 01:52–02:20 | 用 CPU、内存、硬盘类比大模型、上下文窗口和外部历史存储；模型只能处理被调入上下文的信息。 |
| 02:20–03:16 | 引入 Context Orchestrator：负责 Token 预算、优先级和失败回退，并向四类记忆区取数。 |
| 03:16–05:08 | 依次说明短期原文、滚动摘要、长期检索和结构化状态四类记忆。 |
| 05:08–05:36 | 说明状态表是防止长对话“上下文漂移”的稳定锚点。 |
| 05:36–07:00 | 总结系统设计、工程取舍和状态锚点三层思维。 |
| 07:00–08:02 | 给出完整回答，并补充摘要幻觉、检索抖动和召回阈值等线上风险。 |

## 2. 视频的核心架构

### 2.1 模型只是计算单元，记忆调度决定它能看到什么

视频采用如下类比：

| 计算机系统 | 多轮 Agent |
|---|---|
| CPU | 大模型推理引擎 |
| RAM | 当前上下文窗口 |
| 硬盘 | 历史对话、摘要库和向量索引 |
| 内存管理器 | Context Orchestrator |

这个类比的重点是：外部存储中的信息不会自动成为模型记忆。只有经过筛选、排序和预算裁剪后被拼进 Prompt 的内容，才会影响本轮推理。因此，长对话能力首先是上下文管理问题，其次才是模型窗口大小问题。

### 2.2 Context Orchestrator

每次收到新消息，调度器同时回答四个问题：

1. 最近几轮原文需要保留多少；
2. 应注入哪一版历史摘要，是否需要生成新摘要；
3. 外部记忆中是否有与当前问题相关的旧片段；
4. 哪些用户信息、任务状态和已确认事实必须固定注入。

调度器承担三项职责：Token 预算分配、记忆优先级排序、超时或缺失时的降级。任何一层失败都不应让整条对话阻塞。

### 2.3 四类记忆

| 记忆层 | 视频示例预算 | 保存内容 | 价值 | 主要风险 |
|---|---:|---|---|---|
| 短期原文 | 2,500 | 最近 3～5 轮原始消息 | 信息最完整，适合指代、省略和紧邻步骤 | 最耗 Token；移出窗口后不能只靠原文恢复 |
| 中期摘要 | 1,500 | 旧摘要与新移出消息递归合并后的滚动摘要 | 用较少 Token 保留目标、结论和未完成事项 | 摘要是有损生成，可能遗漏或引入错误，并可能递归放大 |
| 长期外挂 | 2,000 | 对历史片段建立向量索引，按当前问题检索 | 让早期细节按需重新进入上下文 | 召回遗漏、相似但无关片段、排序抖动 |
| 状态管理 | 500 | 姓名、偏好、当前任务进度、已确认事实 | 作为不能被摘要或检索稀释的锚点 | 状态更新错误会稳定地传播到后续所有轮次 |

视频建议边对话边滚动压缩，而不是等对话结束再总结。长期检索把有限窗口变成“按需读取历史”的接口；状态表则负责保证核心身份、约束和任务进度不随轮次漂移。

### 2.4 原方案的预算缺口

视频四块预算相加只有 6,500 Token，而不是 8,000 Token：

$$
2500 + 1500 + 2000 + 500 = 6500
$$

剩余 1,500 Token 在视频中没有被明确分配。它不能被视为可随意填满的空白，因为一次真实调用还必须容纳系统规则、当前用户消息、工具候选、输出格式以及模型输出余量。更严谨的预算约束应为：

$$
B_{total} = B_{fixed} + B_{current} + B_{state} + B_{recent} + B_{summary} + B_{retrieved} + B_{output}
$$

其中固定规则、当前请求、状态表和输出余量属于硬预算；近期原文、摘要和检索记忆在剩余预算内动态竞争。视频中的 2,500/1,500/2,000/500 是经验起点，不是可以直接搬用的理论最优值。

## 3. 怎样接入当前 100 工具项目

### 3.1 先明确当前边界

当前项目解决的是单轮 `query → 有序工具 ID 轨迹`，canonical 链路为：

`Intent → easy2/BM25 一级融合 → exact Top-20 Reranker → 二级 RRF → Planner Top-10`。

Planner 的输出严格是 `{"tools":[...]}`，不生成面向用户的自然语言回复，也不预测工具参数和工具返回值。因此，本项目需要的不是通用聊天记忆，而是**多轮工具规划状态**：保存上一轮涉及的任务、对象类型、已选工具、未完成诉求、否定和修正，使当前省略句能够恢复为一个自包含工具请求。

现有实测也说明不需要按视频的 8K 方案设计：

| 冻结评测 | 输入 Token p50 / p95 / p99 / max | 输出 Token p50 / p99 / max |
|---|---:|---:|
| Legacy 6K，最终 DPO Planner + RAG | 449 / 528 / 551 / 594 | 12 / 37 / 46 |
| API 1K，最终 DPO Planner + RAG | 465 / 525 / 564 / 583 | 18 / 34 / 36 |
| 独立 Planner dev 1.2K，最终 DPO checkpoint | 448 / 529 / 553 / 584 | 12 / 37 / 42 |

数值来自 `assignment3_planner_dpo2_20260808` 的最终 Legacy/API 与独立 dev `rag.metrics.json`；训练长度来自当前 Planner 配置。它们是预算设计依据，不是多轮实验结果。

当前 Planner 训练 `max_length=2048`，而单轮 Prompt 的 p99 约 550 Token。开发网格进一步比较了 640/768/1,024 三个常态输入目标，三者没有触发不同裁剪，质量完全相同，因此最终选择**常态输入目标 640 Token、硬上限 1,024 Token、输出预留 96 Token**。内部会话存储可以更大，但每轮只把与工具选择直接相关的信息序列化给模型。

### 3.2 两种 RAG 必须分开

| 系统 | 检索对象 | 目的 | 当前状态 |
|---|---|---|---|
| 工具 RAG | 100 个工具定义 | 找到本轮可能调用的工具 | 已有 canonical 路线，暂时冻结 |
| 记忆检索 | 某个会话的历史工具诉求、修正和计划摘要 | 补全当前省略或远距离引用 | 已实现会话内精确 turn + BM25；未启用向量模型 |

两者应使用独立语料、索引、召回指标和缓存。历史工具不能直接作为当前标签注入；只有当用户明确说“继续刚才的”“还是第三轮那个方案”等内容时，历史计划才可以作为解析证据，否则会造成工具惯性和额外调用。

### 3.3 建议的数据流

```text
新消息
  ↓
读取 CompactToolState + 最近 2 条工具事件
  ↓
必要时检索远期摘要，解析指代、继承、否定和修正
  ↓
生成不超过 128 个增量 Token 的 resolved_query
  ↓
若每个目标都以唯一 catalog 能力名结尾，则直接确定工具
  ↓ 否则
Intent + 当前 canonical 工具检索，得到 Top-10 工具候选
  ↓
按原单轮 Prompt 模板调用 Qwen3 Planner
  ↓
输出 {"tools":[...]} → 单工具目标归并 → 追加 PlanEvent → 更新工具状态与摘要
```

`resolved_query` 是本方案唯一进入现有算法链的记忆载体。它只补全影响工具选择的内容，并记录引用的 turn；商品颜色、订单号等若不改变工具 ID，就不重复塞入 Prompt。初版不生成用户回复、不声称工具已经执行，也不把“已规划”误写成“已完成”。

### 3.4 视频知识的取舍与项目适配

| 视频中的做法 | 本项目是否采用 | 具体处理 |
|---|---|---|
| Context Orchestrator 统一分配上下文预算 | 采用 | 在模型外决定是否读历史、选哪段证据、怎样缩短 query，以及何时拒绝调用 Planner。 |
| 短期原文、滚动摘要、长期检索、结构化状态四层记忆 | 采用其分层思想 | 分别落为近期工具事件、确定性工具摘要、会话内长期计划记忆和紧凑工具状态。 |
| 滑动窗口与边对话边压缩 | 采用 | 超出近期窗口的事件进入摘要和长期索引，原事件仍保留用于审计。 |
| 长期记忆按需召回、失败时降级 | 采用 | 只有远期引用才查精确 turn/BM25；超时或无来源时安全返回空工具，不猜测历史。 |
| 8K 窗口及 2,500/1,500/2,000/500 固定预算 | 不直接采用 | 当前任务的真实 Prompt 最大值远低于 1,024 Token，照搬会增加无关历史和计算量。 |
| 保存完整 user/assistant 对话并一起拼 Prompt | 不采用 | 项目没有自然语言对话回复，只保存会影响工具 ID 和顺序的用户目标、来源与规划结果。 |
| 用 LLM 自由生成递归摘要 | 暂不采用 | 自由摘要会把错误稳定写入后续工具决策；当前使用可追溯的确定性 reducer。 |
| 所有历史统一做向量检索 | 暂不采用 | 工具 Embedding 不等于记忆 Embedding；当前会话规模下精确 turn + BM25 更可控，尚无实验支持增加独立向量模型。 |
| 通用用户画像、情感和闲聊记忆 | 不适用 | 只维护工具规划状态，不推断永久偏好，也不保存与工具选择无关的信息。 |
| 已执行工具与工具返回值记忆 | 目前无法使用 | 本仓库只预测工具 ID，没有参数生成和真实执行器，事件只能标记为 `planned_tools`。 |

适配后的关键变化是：记忆不直接占据 Planner 的多段 Prompt，而是在模型外被压缩成一个短 `resolved_query`；Intent、检索、Reranker、Top-10、Planner 权重和 Prompt 本身不改。普通自然请求仍走原单轮链路，只有完整 catalog 能力名构成的严格结构化请求进入可审计快速路径。

## 4. 最小记忆数据结构

只保存会影响工具 ID 或工具顺序的信息，不建立通用用户画像。

### 4.1 工具事件 `PlanEvent`

- `conversation_id`、`turn_id`、时间戳；
- 当前原始 query 与最终 `resolved_query`；
- 本轮解析出的目标、否定、修正和引用来源；
- Planner 输出的有序工具 ID；
- Prompt、模型、检索路线和版本哈希。

`PlanEvent` 是审计真相。Planner 输出只能记为 `planned_tools`；由于当前项目没有工具执行器，不能记成“已调用”或“已完成”。

### 4.2 紧凑工具状态 `CompactToolState`

- `last_request_goals` 与上一轮用户要求的顺序，仅用于被引用；
- `explicitly_carried_goals`、`cancelled_goals`；
- `last_planned_tools`，只作审计证据，不生成用户目标；
- 从当前计划派生的 `active_domains`、从 query 提取的 `active_object_types`；
- 每个目标的 `source_turn_ids`、状态更新时间、最后 turn 和单调递增版本号。

订单号、颜色、预算等实体目前保留在有来源的目标文本中，不另建通用用户画像或无依据的置信度字段。状态输出受 JSON Schema 约束；当前明确陈述优先于历史状态，否定和修正会生成单独记录并从本轮有效目标中移除。

默认规则是**上一轮目标不自动带入下一轮**。只有当前 query 出现明确继承、引用或修正信号时，才从 `last_request_goals` 或长期摘要恢复目标。Planner 预测只能更新 `last_planned_tools`，不能反过来把一次可能错误的预测固化成用户目标。

### 4.3 近期工具账本 `RecentPlanLedger`

保存最近 2 条紧凑记录：`turn_id + 用户诉求摘要 + planned_tools + 修正动作`。不保存冗长 assistant 文本，也不把完整候选工具列表重复写入记忆。

### 4.4 滚动工具摘要 `ToolRollingSummary`

- 覆盖的 turn 范围和上一版摘要版本；
- 仍有效的目标、已取消目标、历史决定和未解决引用；
- 对应来源 turn；
- 生成方式和版本。

当前版本只用确定性 reducer 从结构化事件合并摘要，不让 LLM 自由改写，也没有接入第二个摘要模型。摘要保存历史目标、取消目标、覆盖到的 turn 和版本；每个目标仍能追溯到来源 turn。

### 4.5 长期计划记忆 `LongTermPlanMemory`

- 已滑出近期窗口的目标文本、历史工具计划和来源 turn；
- domain、tool IDs、创建时间和过期时间；
- 用于精确 turn/BM25 检索的文本。

当前版本会为每条滑出窗口的非闲聊工具事件建立一条紧凑记录，以支持“回到第 N 轮”的精确恢复；它不会从一次请求推断永久用户偏好。原始事件仍留在事件表，长期记录受会话隔离、30 天 TTL 和整会话删除控制。

## 5. 短期记忆、压缩与 Token 预算

### 5.1 内部滑动窗口

开发阶段比较了最近 2/3/4 条 `PlanEvent`，最终窗口为 2 条。它是解析器的内部输入，不直接拼给 Planner。若当前 query 已经自包含，本轮完全跳过历史读取；只有出现指代、继承、否定、修正或“继续之前任务”等信号时才读取状态。

每轮先确定 `context_mode=none/recent/long`：完整独立请求使用 `none`；引用最近任务使用 `recent`；明确引用较早轮次且近期无法解析时才使用 `long`。这样可以把记忆干扰限制在真正依赖上下文的样本上。

当前实现以固定事件窗口作为唯一压缩触发器。第 3 条新事件写入时，第 1 条事件开始进入滚动摘要和长期记录；以后每轮向前推进一条：

1. 把即将移出的完整事件交给确定性 reducer；
2. 更新 `ToolRollingSummary`；
3. 保留仍有效目标、取消记录和来源 turn；
4. 原始 `PlanEvent` 继续保留在 SQLite 中用于审计，但不会再读入近期解析窗口。

因此这里的“压缩”是减少在线读取和新建紧凑索引，不是删除事件真相。按 Token 压力、任务阶段或分支切换的自适应触发尚未实验，不作为当前已实现能力。

### 5.2 最终在线预算

现有三组最终 Planner 评测的输入 p99 不超过 564 Token、最大 594 Token，输出最大 46 Token。因此采用两级限制：

| 项目 | 最终约束 |
|---|---:|
| 原始 query 字符上限 | 4,096 |
| 正常 Planner 输入目标 | ≤ 640 Token |
| Planner 输入硬上限 | ≤ 1,024 Token |
| `resolved_query` 相对当前 query 的增量 | ≤ 128 Token |
| Planner 输出预留 | 96 Token |
| SFT 总长度上限 | 2,048 Token，不作为日常填充目标 |

动态预算为：

$$
B_{extra} = \max\left(0, 640 - T(\text{system} + \text{Top10 tools} + \text{current query})\right)
$$

`CompactToolState`、近期账本和长期摘要都留在系统内部，只有 resolver 选出的必要目标进入 `resolved_query`。运行时按“完整改写、仅有效目标、原始 query”的顺序尝试；每个 query 版本都重新走工具检索并用 Planner 的真实 tokenizer 计数。640 是软目标，超过时记录告警；若改写相对同候选下的原 query 增加超过 128 Token，则尝试更短版本；若连原 query 都超过 1,024 Token，则不调用 Planner，并把拒绝原因写入事件。

自然短会话评测对 A、C～L 固定使用 640 Token 常态输入目标。该评测验证这一预算下各记忆模块的相对表现，不将 640 表述为已证明的全局最优值。正常输入目标与输出预留之和为 736 Token，对 2,048 的 SFT 长度上限保留充足余量；直接拼接基线 B 单独放宽到 4,096 Token，避免预算差异压低基线。

## 6. 长期记忆按需检索

长期检索不是每轮固定步骤。显式“第 N 轮”、最开始、早些时候、历史任务等明确远期信号才优先进入长期路径；“刚才、上一轮、上一步、照旧”与泛化词“之前”同时出现时优先解释为近期引用，避免把“刚才的之前方案”误送入 BM25。近期状态无法解析明确远期对象时，才读取长期记录。

读取顺序为“会话隔离与 TTL 过滤 → 可直接解析的来源，否则对象锚点/BM25 → 去重”，长期记忆 Top-k 固定为 2，不使用独立测试集选参。开发集从 C 的 50.2% 回放提高到 E 的 85.5%，表明规则摘要和按需记忆都有增益，但不单独证明 Top-k=2 的最优性。系统只抽取有来源的目标；业务域和工具信息会保存，但不会在缺少明确条件时擅自过滤。现有 `easy2` Embedding 专用于工具描述检索，不在未经独立实验时兼任会话记忆模型。

冲突优先级为：

`当前明确陈述 > 当前否定/修正 > CompactToolState > 近期账本 > 滚动摘要 > 长期检索结果`。

需要防御的主要失败包括：

- 摘要幻觉经过递归压缩不断放大；
- 召回结果轻微变化导致相邻轮回答不一致；
- 旧计划覆盖用户刚刚给出的新要求；
- 无关历史诱导 Planner 重复调用过去的工具；
- 记忆检索把历史 `planned_tools` 误当当前 gold；
- 摘要或检索服务超时导致规划阻塞；
- 跨用户数据串读以及敏感信息长期保留。

因此需要超时降级、来源追踪、会话隔离、TTL 和删除接口。长期检索失败时，系统只使用当前 query 和仍可明确解析的近期紧凑状态；纯引用且找不到可靠来源时标记 `unresolved_reference`，返回合法空工具结果，并跳过 Intent、工具检索和 Planner。它不会猜测另一段历史，也不会污染上一版状态。

## 7. Planner Prompt 保持单轮形态

最终不采用“系统规则 + 状态 + 摘要 + 历史原文 + 长期片段”的大 Prompt。Context Orchestrator 在模型外完成选择和压缩。普通请求仍由 Planner 接收当前已训练过的两段结构：

1. 原 `SYSTEM_PROMPT` 与 JSON 输出约束；
2. `Top-10 候选工具 + resolved_query`。

例如：

```text
Turn 1：先查这个订单的物流，再估计什么时候到。
计划：get_order_logistics → estimate_delivery_time

Turn 2：物流不用查了，只看什么时候到。
resolved_query：对于当前订单，只估算预计送达时间，不再查询物流详情。
计划：estimate_delivery_time
```

历史文本、历史候选工具和旧 Planner 输出不直接拼进 Prompt。这样既减少 Token，也尽量保持现有 SFT Prompt 分布。`resolved_query` 必须同时保存原 query、引用来源和变换记录，便于发现错误继承。

另有一条严格受限的快速路径：只有解析后的每个目标都以“核实/确认 + 这件……的 + 唯一完整 `keyword_label`”构成时，才按完整 100 工具 catalog 做最长唯一匹配并跳过 Intent、检索和 Planner；任一目标不满足即整轮回退原链。它用于消除结构化 catalog 别名样本中的无谓模型误差，不扩展到自然语言近义词。

自然语言中的“继续刚才那些事”属于另一种情况：它不是重新表达任务，而是对某一完整历史轮次的精确重放。当前工程实现先恢复该轮实际送给 Planner 的 query；若来源事件同时满足成功、严格输出、工具非空，并且检索版本、路线哈希和 Agent 配置哈希都与当前运行时一致，则直接复用该轮有序工具计划。任一条件不满足就只重放 query，并重新执行 Intent、检索和 Planner。这条缓存不用于部分修改、取消或多个来源轮次的合并。2026-08-16 的自然短会话测试中，该路径在 612 个回放目标上命中 594 次，Planner 仅调用 16 次，另有 2 条可靠来源未解析。

初版使用确定性模板序列化，例如“上一轮有效诉求 + 当前取消项 + 当前新增项”，不增加第二次自由生成。只有 dev badcase 证明规则无法覆盖复杂指代时，才增加一个输出固定 JSON Schema 的 resolver，并把它的准确率、延迟和 Token 单独报告。

若实验显示只改写 query 仍不足，才能定义新的带结构化 `tool_context` 的 Prompt 版本，并为它构造多轮 SFT 数据；不能静默改变现有 prompt version 后继续沿用原指标。

## 8. 自然短会话记忆评测

评测使用 2～7 个用户轮、记忆距离 1～5 的自然短会话，在不查看测试结果的前提下完成十二候选选型和一次性独立确认。

### 8.1 问题、指标与选择规则

每段会话只计最后一个目标轮，属于两个互斥类型：

- `natural_replay`：当前短句依赖历史，需要找回并完整重放某一来源任务；
- `standalone_switch`：历史后出现语义完整的新任务，系统不得继承旧工具。

工具 ID、数量和顺序全部一致才计为 TraceEM。报告同时给出回放、不继承、两类等权宏平均和本数据集受控混合总分；其中约 60%/40% 的回放/新请求配比是为统计功效分层抽样，**不是线上流量比例**。开发集预注册门槛要求候选的不继承 TraceEM 最多比 A 低 1 个百分点；合格候选依次按更高回放、更高新请求、更低 P95 输入 Token 和更早标签排序。

### 8.3 隔离、预注册与封存

- 相对 42,400 条训练、冻结及独立保护数据，开发和测试的 query、来源 trace ID、表达簇、上下文骨架重合均为 0。
- 开发/测试之间 normalized query、计分目标、来源或干扰 query、完整会话重合均为 0。自然短确认允许在单个 split 内重复，但必须绑定隔离的历史和 gold。
- 工具组合允许重复，因为任务本身是固定 100 工具闭集；冻结数据和独立保护 query 均未作为生成源。
- `design.lock.json`、`protocol.json`、`preregistration.json` 和六个实现文件哈希在正式候选输出前锁定。开发完成并写入 `selection.lock.json` 前，测试候选输出为 0。
- 开发比较 A～L 并锁定 L；测试一次性运行预注册的全部十二候选，只用于确认和展示，不参与任何规则修改。

### 8.4 十二个阶段候选

| 候选 | 本步增加的能力 | 目的 |
|---|---|---|
| A | 不读取历史 | 无记忆安全基线 |
| B | 直接拼接最近两轮 | 验证原文历史的上限与污染风险 |
| C | 结构化近期状态 | 提取最近任务、顺序和来源 |
| D | 规则摘要 | 保存滑出近期窗口的任务摘要 |
| E | 按需记忆检索 | 用对象锚点/BM25 读取更早来源 |
| F | 近期路由优先级 | 避免泛化历史词压过近期信号 |
| G | 请求边界 | 区分历史回放和完整新请求 |
| H | 单工具目标归并 | 修正短确认的单工具解析边界 |
| I | 严格 Catalog 能力名直达 | 可审计的完整能力名快速路径 |
| J | 完整意图恢复 | 找到来源后恢复整轮 `resolved_query` |
| K | 自包含保护 | 多目标新请求不受历史污染 |
| L | 同版本计划缓存 | 来源、版本和计划全有效时复用有序计划 |

十二候选使用同一 Intent、canonical Top-10、Qwen3-8B Planner checkpoint、Prompt、greedy 解码和 Catalog。A 是无历史基线，B 是原文拼接压力基线，C～L 才是逐步累加的结构化记忆主线；因此 B→C 是替换历史处理架构，不是单一模块增量。B 的 4,096 Token 上限保证历史真实进入模型且无预算回退。后端缓存按“完整 query + Top-10 有序列表”的精确哈希去重实际模型调用，不共享标签或答案。

## 10. 工程实现与待改进方向

运行配置标识为 `E3-n2-k2-t640`，包含结构化记忆、边界守门、完整任务恢复与同版本缓存。开发集按预注册规则锁定 L，独立测试得到回放 92.8% 和不继承 97.4%；它是封存评测胜者，但仍只是合成闭集结果，不等同于真实流量生产验收：

1. 最近 2 条 `PlanEvent` 构成短期账本，历史目标默认不自动继承；
2. “刚才说的那些事”“行，按刚才说的办”与对象锚点由自然引用选择器定位来源；工程仍兼容显式轮次，但正式数据不依赖该表达；
3. 订单取消、退款、购物车删除等业务动作保持当前请求身份；没有真实继承/取消目标时不改写原 query；
4. 精确整轮引用先恢复来源轮的 `resolved_query`；同版本、同路线且来源计划有效时复用有序工具计划，否则重新走模型链；
5. 自包含多目标请求即使包含“之前”等业务词，也不会错误读取历史；
6. `CompactToolState` 保存目标、顺序、取消和来源，远期引用最多检索 2 条会话内证据，无来源则安全返回空工具；
7. 每个目标都严格命中完整 catalog 能力名时直接输出工具，否则普通请求仍走 canonical Top-10 和原 Planner Prompt；
8. Planner 输入目标 640 Token，硬上限 1,024，改写增量上限 128，输出预留 96；输出只含有序工具 ID。

视频的四层记忆思想被保留为模型外管理逻辑，但不会把全部历史同时塞进 Prompt。本项目追求的是可追溯地恢复本轮工具目标，并在可识别的结构化请求上绕过不必要推理；对自然语言仍保留完整模型链路和安全回退。

### 11.2 已写死的安全与一致性条件

1. `PROJECT/configs/agent_runtime.json` 锁定 canonical revision 和检索路线 SHA-256；工具 catalog、语料、向量、Embedding/Reranker 及系统 Prompt 按同一路线校验。配置记录实际 Intent/Planner adapter 哈希，不宣称跨环境逐 bit 复现。
2. 自包含 query 的 `context_mode=none`，解析结果必须与原 query 完全相同；“那个订单”等对象指代可读取上下文，但不会因此自动继承旧工具目标。
3. 只有元取消、纯引用或明确恢复旧方案时才继承历史目标；订单取消、退款和购物车删除仍是当前工具目标。Planner 预测只进入 `last_planned_tools`，不会生成用户目标。
4. 每次提交按 `conversation_id + version + turn_id` 做原子比较；并发旧写入被拒绝，不会覆盖较新的会话状态。
5. Planner 调用前使用其真实 tokenizer 复算完整 Prompt。若改写增量超过 128 Token，按信息量依次尝试更短变体并重新检索；所有变体仍超过 1,024 时直接拒绝 Planner 调用。
6. Planner 非法 JSON、候选逃逸或重复工具不写入 `last_planned_tools`；原始输出和错误原因仍保留在事件中审计。
7. 整轮计划缓存同时校验来源状态、严格输出、非空工具、route hash、retrieval revision 和 Agent config hash；任一不一致都回退完整推理链。
8. 长期记忆先按会话过滤；检索超时或异常时退化到近期状态，跨会话读取路径不存在。

### 11.3 使用与验证

只跑不加载模型的架构测试：

```bash
python3 -m unittest discover -s PROJECT/tests -v
python3 PROJECT/scripts/agent/audit_agent_static_regression.py
python3 PROJECT/scripts/agent/audit_agent_failure_guards.py
```

多轮质量证据为计划各 1,000 段、审核保留开发 991/测试 993 段的自然短会话十二候选封存评测；静态链路由 Legacy/API 回归验证。

持续运行 canonical Agent 时，模型只加载一次；每行输入一轮 query，输出仍是包含 `tools` 的结构化结果：

```bash
python3 PROJECT/scripts/agent/run_agent.py run \
  --session demo-001 \
  --interactive \
  --intent-device cuda:0 \
  --embedding-device cuda:0 \
  --reranker-device cuda:1 \
  --planner-device cuda:2
```

查看或删除会话：

```bash
python3 PROJECT/scripts/agent/run_agent.py inspect --session demo-001
python3 PROJECT/scripts/agent/run_agent.py delete --session demo-001
```

当前 Agent 已完成开发 991/独立测试 993 段自然短会话、十二候选开发选型与一次性测试、Legacy/API 静态守门、55 项 Agent 架构测试、故障/边界审计和真实 checkpoint 推理。当前正式结论是：锁定版 L 在独立测试 993 个目标上达到 **94.6%**，其中历史回放 **92.8%**、完整新请求不继承 **97.4%**，并把目标轮 Planner 调用从 993 次降至 394 次。L 相对 A 的新请求点估计低 1.05pp 且配对检验不显著，真实工具执行、参数填充、部分修改、开放域流量和线上多租户仍未覆盖；因此它是当前评测胜者，不是未经影子流量验证即可上线的结论。

部署边界也要分清：当前 SQLite 是本地算法基线，数据库文件权限会收紧为 `0600`，所有查询都按 `conversation_id` 过滤，但调用方仍必须负责用户认证和 conversation 所有权校验；仓库内没有实现数据库加密、敏感字段脱敏、跨机器记忆服务或租户级访问控制。30 天 TTL 和删除接口不能替代这些生产安全措施。
