# 自然短会话记忆评测完整总结：数据集、十二候选与最终结果

> 评测日期：2026-08-16；开发集选型完成，独立测试一次性确认完成，测试集永久封存；唯一机器可读结果为 `PROJECT/data/agent/_aux/natural_short_memory_evaluation/results_final.json`。

## 1. 一页结论

评测数据符合电商短会话的使用习惯：每段 2～7 个用户轮，历史回放最多跨 5 轮，不出现“调用第 N 轮”“完整原样重做”等评测腔。开发/测试各计划 1,000 段，经过独立语义审核后保留 991/993 段。

最终在开发集锁定 `L：同版本计划缓存`，再一次性打开独立测试：

| 最终指标 | 结果 | 95% Wilson 区间 |
|---|---:|---:|
| 受控混合目标 TraceEM | **939/993 = 94.56%** | 92.97%～95.81% |
| 自然历史回放 TraceEM | **568/612 = 92.81%** | 90.49%～94.60% |
| 完整新请求不继承 TraceEM | **371/381 = 97.38%** | 95.24%～98.57% |
| 回放/不继承等权宏平均 | **95.09%** | — |
| 来源轮精确命中 | **583/612 = 95.26%** | — |
| 目标轮 Planner 调用 | **993 → 394，减少 60.3%** | — |

L 相对不读取历史的 A 改善 538 条、回退 6 条，净增 532 条，即 **+53.58pp**；相对直接拼接 B 改善 460 条、回退 22 条，净增 438 条，即 **+44.11pp**。正式 24 个候选运行共生成 67,536 条逐轮预测，后端错误为 0。

需要同时保留一个安全边界：L 在独立测试的完整新请求上为 371/381，A 为 375/381，L 点估计低 **1.05pp**；逐条配对是 4 条净回退、双侧 McNemar $p=0.125$。因此 L 是封存评测胜者，不等于已经完成真实流量上线验收。

## 2. 评测目标与范围

评测同时考察两种相反的能力：当当前短句信息不足时，系统必须定位正确来源轮并恢复完整工具任务；当当前请求已经自包含时，系统必须保持新请求边界，不继承无关工具。

因此数据集分别报告 `natural_replay` 和 `standalone_switch`，并在开发集上使用双指标规则选型。独立测试只用于一次性确认，不用于调整数据、规则、候选顺序或门槛。

## 3. 从第一性原理定义评测

### 3.1 可以观察什么

对每个用户轮，评测可以直接观察：

- 当前 query 与同一会话内此前的用户请求；
- 当前轮是否依赖历史，以及唯一来源轮；
- 来源任务和当前任务的标准有序工具链；
- 候选选择的来源轮、`resolved_query`、Top-10 和最终有序工具链；
- 是否调用 Planner、是否命中经过验证的计划缓存；
- 严格输出、Token、错误状态和逐条改善/回退。

### 3.2 可以控制什么

本协议控制了会话长度、回放距离、表达族、工具数、干扰任务、生成模型、审核模型、数据隔离、固定后端和候选启用模块。所有候选接收完全相同的会话和 gold，只改变 Planner 之前的历史处理。

### 3.3 要保证什么

评测需要同时保证两件事：

1. 需要历史时，系统找对来源并恢复完整工具任务；
2. 当前 query 已经自包含时，系统不把旧工具错误继承进来。

只测第一项会奖励无条件拼接，只测第二项又会奖励完全不读历史。因此本次始终分开报告 `natural_replay` 与 `standalone_switch`，并只在开发集上按预注册双指标规则选型。

## 4. 数据集设计

### 4.1 评测单元

每段独立会话只统计最后一个目标轮；此前轮次实际执行并写入记忆，但不进入候选选型主分数。目标分为：

- `natural_replay`：当前短句信息不足，必须从历史恢复某一整轮任务；
- `standalone_switch`：此前存在无关历史，但当前请求本身完整，必须保持不继承。

历史轮仍有标准工具链，用来真实建立状态、摘要、长期记录和来源计划。开发集实际执行 2,793 轮，其中目标 991 轮、普通历史 1,802 轮；测试集实际执行 2,835 轮，其中目标 993 轮、普通历史 1,842 轮。

## 5. 数据生成、审核与隔离

### 5.1 生成流程

数据在任何正式候选预测产生之前依次完成：

1. 用固定 seed `2026081601` 采样目标类型、距离、来源位置、工具数和干扰深度；
2. 先生成不含 query 的来源/干扰工具计划，避免直接从旧 query 复制表达；
3. `gpt-5.4-mini` 为来源和干扰任务生成自然 API 风格电商请求；
4. `gpt-5.4-mini` 基于完整会话生成目标 query；
5. 静态规则拒绝评测腔、错误近期关系、缺少整体范围和泄漏动作细节的表达；
6. 独立 `gpt-5.5` 判断是否自然、是否唯一指向来源、是否完整保持来源动作；
7. 通过审核的会话装配为逐轮 JSONL，再执行保护集与开发/测试隔离审计；
8. 写入 `protocol.json` 和 `preregistration.json` 后，才允许运行候选。

生成 prompt 标识为 `natural-short-memory-target-generator`，审核 prompt 标识为 `natural-short-memory-target-judge`；各类型 prompt 的 SHA256 均记录在 `protocol.json`。

### 5.2 排除规则

开发和测试共排除 16 个无法在最大尝试次数内通过自然性或语义清晰度审核的回放计划：

- 开发：`prodmem_dev_00197/00352/00415/00529/00626/00628/00684/00860/00918`；
- 测试：`prodmem_test_00042/00256/00518/00674/00756/00928/00949`。

主要原因是整体来源范围仍有歧义、对象近期关系不成立、确认句不是真正的隐式确认，或独立审核不认可唯一指向。统一规则要求每个 split 至少接纳 98%；所有排除 ID、20/24 次尝试和逐项原因完整保留，没有事后补成更容易的样本。

## 6. 指标、选型与公平性

### 6.1 严格指标

主指标是有序工具链完全匹配：

$$
\mathrm{TraceEM}(y,\hat{y})=\mathbf{1}[\,|y|=|\hat{y}|\ \land\ \forall i,\ y_i=\hat{y}_i\,]
$$

任何工具遗漏、多选、替换或顺序变化都记为 0。报告使用：

- `replay TraceEM`：只统计自然历史回放；
- `no-inherit TraceEM`：只统计完整新请求；
- `balanced macro`：两者等权平均；
- `observed mixture`：按本受控数据 60%/40% 的实际比例汇总，仅用于展示。

### 6.2 开发选型规则

开发集 A 的不继承 TraceEM 为 97.668%。候选必须达到至少 96.668%，然后依次比较：

1. 更高回放 TraceEM；
2. 更高完整新请求 TraceEM；
3. 更低 P95 输入 Token；
4. 更早候选标签。

因此混合分数从来不是锁定 L 的依据。L 在开发集不继承为 97.409%，比 A 低 0.259pp，位于 1pp 非劣容忍带内；其回放 96.033% 为所有合格候选最高。

### 6.3 固定不变的组件

十二候选固定使用：

- 同一 100 工具 Catalog；
- 同一 canonical BM25/Vector RRF → Top-20 Reranker → 二级 RRF Top-10；
- 同一 Qwen3-8B Planner `checkpoint-113`；
- 同一 Planner Prompt、Top-10 原始顺序和 greedy 解码；
- 全部样本固定为电商类，Intent 路由不参与候选差异；
- C～L 的 Planner 输入软目标 640、硬上限 1,024；
- B 单独放宽到 4,096，并强制真实带入最近两轮，预算回退为 0。

后端缓存只按“完整 query + 有序 Top-10”的精确哈希去重相同推理输入，内容来自真实检索和真实 Planner 输出，不读取 gold，不允许不同输入共享答案。

### 6.4 封存顺序

`design.lock.json`、`protocol.json`、`preregistration.json` 和六个实现文件哈希先锁定；开发集运行十二候选并写入 `selection.lock.json` 时，测试候选预测文件数量为 0。锁定 L 后，测试才一次性运行预注册的全部十二候选。测试结果没有用于修改实现、数据、门槛或候选顺序。

## 7. 十二候选的详细做法

候选序列包含两条基线和一条结构化主线：A 是无历史基线，B 是原文拼接压力基线；C～L 才是逐步累加的结构化记忆主线。因此 B→C 表示“以结构化状态替换直接拼接”，不是在 B 上再加一个模块。

### A：不读取历史 `a_stateless`

- 强制 `context_mode=none`，当前 query 原样进入固定检索与 Planner。
- 作用：测量单轮系统对自然短句的偶然猜中率，以及完整新请求的安全上限。
- 预期：完整新请求高，历史回放接近 0。
- 测试：混合 41.0%，回放 5.2%，不继承 98.4%。

### B：直接拼接最近两轮 `b_direct_concat`

- 读取最近 2 个事件，把历史原始请求与当前 query 直接合并后送入检索和 Planner。
- 4,096 Token 预算确保历史真实进入模型，不允许回退成只看当前短句。
- 作用：验证原始历史确实有用，并量化无条件拼接的污染和成本。
- 风险：Planner 需要自己判断哪一段是当前任务，完整新请求容易把旧工具一起输出。
- 测试：回放升至 59.2%，但不继承跌至 36.5%；目标 P95 输入从 A 的 511.4 增至 665.4 Token，严格输出率降至 98.99%。

### C：结构化近期状态 `c_structured_recent`

- 不再向 Planner直接塞历史原文；保存最近 2 个 `PlanEvent`，解析当前目标、继承目标、取消目标和来源轮。
- 用确定性 `resolved_query` 表达有效目标，并保留原 query 作为预算回退变体。
- 自然整轮引用使用对象锚点/BM25 语义策略，但 C 没有摘要和全会话长期记录，主要依赖近期状态。
- 测试：来源轮命中 55.1%，回放 48.0%，不继承恢复到 86.9%；混合 62.9%。它比 B 的回放低，但因大幅减少历史污染，混合正确数净增 124。

### D：加入规则摘要 `d_rule_summary`

- 在 C 上加入 `ToolRollingSummary`：事件滑出最近两轮后，确定性保存历史目标、取消项和来源轮。
- 长期模式优先从摘要中恢复旧目标，不递归调用 LLM 生成摘要。
- 作用：让距离 3～5 的任务不因近期窗口淘汰而消失。
- 测试：来源轮命中从 55.1% 升至 75.0%，回放从 48.0% 升至 66.2%；相对 C 改善 111 条、回退 0 条。

### E：加入按需记忆检索 `e_long_memory`

- 在 D 上把会话事件写成可检索的 `MemoryRecord`，保存来源 turn、`resolved_query`、目标和当时的已规划工具；后续能否复用计划由 J/L 的更严格条件另行判断。
- 只有路由为 long 时检索；自然确认直接选最近有效事件，其他引用先删除“继续、前面说的”等元话语，再用对象锚点/BM25 排序，Top-k 固定为 2。
- 零词面证据时不返回历史，并始终按 `conversation_id` 隔离。
- 测试：来源轮命中 95.1%，回放 84.6%，混合 85.5%；相对 D 改善 120 条、回退 7 条。

### F：加入近期路由优先级 `f_route_precedence`

- 当 query 同时出现近期信号和泛化历史词时，让“刚才、上一条”等近期信号优先于“之前”等宽泛词；强远期信号仍走 long。
- 作用：防止“刚才说的之前那个方案”等复合说法被错误送入长期检索。
- 当前语料的引用关系已较清晰，测试相对 E 改善/回退均为 0；这是质量中性的路由防御，不能从本数据宣称额外增益。

### G：加入请求边界 `g_request_boundary`

- 区分“取消上一项任务”这种元取消与“取消订单、申请退款、删除购物车商品”等当前业务动作。
- 完整当前请求若没有可靠继承目标，就保留原 query，不把历史目标自动并入。
- 无历史的首轮即使包含“之前”等业务时间词，也按独立请求处理。
- 测试：不继承从 86.9% 升至 97.4%，回放从 84.6% 升至 88.6%；相对 F 改善 67 条、回退 3 条，混合增加 6.45pp。

### H：加入单工具目标归并 `h_single_tool_normalization`

- 对无历史、无取消、Planner 严格输出单一工具的当前轮，把被规则切碎的多个短 clause 重新归并为一个以原 query 表示的完整目标。
- 作用：使后续“按刚才说的办”继承完整单工具意图，而不是继承某个碎片。
- 测试：相对 G 改善 5 条、回退 0 条，回放升至 89.4%，混合 92.4%。

### I：加入严格 Catalog 能力名直达 `i_catalog_alias`

- 只有每个解析目标都严格命中完整 Catalog 能力名时，才绕过 Intent、检索和 Planner，直接输出对应工具。
- 任一目标不是严格完整能力名，就整轮回退普通 canonical 链路；不做自然语言模糊别名猜测。
- 当前自然测试没有形成额外正确数，相对 H 改善/回退均为 0；它是结构化 API 输入的可审计快速路径。

### J：加入完整意图恢复 `j_whole_turn_recovery`

- 当且仅当系统识别为单一来源的整轮回放、没有当前新增目标和取消项时，读取来源事件实际使用的完整 `resolved_query`。
- 将该来源 query 放在 Planner 输入变体首位，并允许可信整轮重放越过“相对原短句最多增加 128 Token”的普通增量限制，但仍受 1,024 硬上限约束。
- 作用：来源轮找对后不再把目标碎片重新拼接，而是完整恢复原任务语义和顺序。
- 测试：相对 I 改善 25 条、回退 4 条，回放从 89.4% 升至 92.8%，混合升至 94.6%；严格输出率达到 100%。

### K：加入自包含保护 `k_standalone_guard`

- 若当前解析出至少 2 个完整新目标、没有继承或取消目标，也没有显式轮次引用，则强制重置为 `context_mode=none` 并清空历史证据重新解析。
- 作用：防止包含“之前、再、顺便”等词的完整多目标新请求误触发历史。
- 当前测试的目标工具链正确性与 J 完全一致；模块改变了少量内部路由诊断，但没有改变主指标，保留为面向更复杂自包含请求的安全守门。

### L：加入同版本计划缓存 `l_final_cache`

- 只有整轮来源事件满足 `status=ok`、严格输出、工具非空，并且 route hash、retrieval revision、Agent config hash 全部与当前运行时一致，才复用来源的有序工具计划。
- 任一校验失败就只重放完整 query，重新运行检索与 Planner；部分修改、取消、多来源合并都不使用缓存。
- 测试与 K 准确率完全一致，但 993 个目标中命中 597 次版本一致性缓存，Planner 调用从 991 次降至 394 次；单看 612 个回放目标，594 次命中缓存、16 次调用 Planner、2 次来源未解析。另有 3 个完整新请求被语义路由误判为回放后命中缓存且全部错误，说明“缓存版本有效”不能替代“当前句确实引用历史”的语义判断。

## 12. 能得出什么，不能得出什么

### 12.1 可以得出的结论

1. 无条件直接拼接能解决部分近期引用，但会显著污染完整新请求，不适合作为生产方案。
2. 从结构化近期状态到摘要、按需检索、请求边界和整轮恢复，每个关键阶段都在独立测试复现了增益。
3. 最大的质量贡献来自摘要、长期来源检索、请求边界和完整意图恢复。
4. 经过严格版本校验的计划缓存可以在准确率不变时减少 60.3% 的目标轮 Planner 调用。
5. 当前主要错误已经从“完全找不到历史”收敛到少量来源轮定位失败和来源 Planner 自身错误。

### 12.2 不能外推的结论

1. 94.6% 是受控 60%/40% 混合比例，不是线上准确率预测。
2. 数据来自 API 模型生成并经模型审核，不是真实用户日志。
3. 只覆盖固定 100 工具闭集、整轮完整回放和完整新请求切换。
4. 不覆盖部分继承、参数共指、增删改某一步、真实取消合并、工具参数生成和真实 API 执行成功率。
5. 不覆盖开放域聊天、几十轮长会话和生产多租户权限安全。
6. 测试不继承比 A 低 1.05pp，虽无统计显著性，仍需要真实影子流量确认。

因此推荐状态是：L 作为多轮评测锁定方案和后续影子验证候选；不把它描述成已经完成线上 canonical 晋升。
